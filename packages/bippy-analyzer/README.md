# bippy-analyzer

Finds every state a React app can be in by reading its source, then checks that answer against real renders. See [GOAL.md](GOAL.md) for why.

- **Analyzer** (`src/core`, on the React Compiler's own source in `src/react-compiler`) reads a project with the TypeScript 7 checker, without running it. For each component it prints the data it depends on, its render tree, and its states with the actions between them. See [docs/symbolic-tree.md](docs/symbolic-tree.md).
- **Verifier** (`conformance/verifier`) checks those claims in a real browser.
- **Conformance** (`conformance/`) runs both on pinned open-source repos. See [conformance/README.md](conformance/README.md).

```sh
pnpm --filter bippy-analyzer analyze tests/fixtures/symbolic-tree/tsconfig.json -c Wizard
pnpm --filter bippy-analyzer conformance verify tests/fixtures/symbolic-tree/tsconfig.json
pnpm --filter bippy-analyzer conformance run --env vercel -n 8
```

## How verification works

For each exported component:

1. **Instrument.** A Vite dev server serves the app's own code, with a probe on every branch the analyzer modeled and every place a mutation warning points at.
2. **Mount.** Playwright opens a page that loads bippy before React and mounts the component inside the providers the app installs (React Query, a React Router data router, a TanStack Router, react-hook-form, nuqs, next-intl, React Flow, a signed-in next-auth session, and the app's own Redux store). The harness supplies what apps expect from their real environment: Node globals, placeholder env variables, stubs for `next/font`, `next/navigation`, `next/router`, `next/document` and `server-only` along with Next's router contexts, and server actions that do nothing, as a client bundle gets them. It also accepts what Next's bundler allows and Vite doesn't: `require` calls and CommonJS modules in the app's own code. Stylesheets load empty, since fibers don't depend on them. Every dependency is pre-bundled before the first mount, a `require` of a package that isn't installed throws only where it runs, and navigations a script starts are cancelled. When a component throws for want of a parent, like "`DialogTitle` must be used within `Dialog`", it is mounted again inside that parent. The parent comes from the project (nearest file first), the packages and namespaces of parts the component or a file it imports by relative path imports, or its own file's compound root and other parts. It goes just outside whichever mounted component threw, read from React's component stack. A parent named for a library part the component's own root renders, like a vaul `DrawerTitle` asking for Radix's `Dialog`, is first that root, and a parent that throws the same error itself gets one of its own parts around it, like a `MessageScroller` its `MessageScrollerProvider`. A parent from the project mounts with the props its own analysis samples, and a context's provider with a sample of the value the component reads from it. An error that names no parent, like a hook's context being `null`, gets the providers of the contexts the component reads, starting with one named after the hook, like `UIAppStateContext` for `useUIAppState(...)`, which a child it renders may read. A parent that doesn't render the component at all, like a part that renders nothing until something is selected, gives way to its next candidate. A parent added earlier that then throws for want of data, once a parent added outside it provides what it stood in for, like a bare `Toast.Root` inside the app's own `Toast`, is dropped. An app that renders its own router, like its `App`, mounts outside the harness's. An async server component is awaited in the page, along with those it renders, and mounted as what it returned. Server SDKs like Prisma, Stripe or next-auth's server side, modules the app imports but doesn't have, like an undeclared package or a file missing from the repo, and an app's requests to other origins, are answered with stand-ins for any value, and `next/headers`, `next/cache`, `next-intl/server`, nuqs's server cache and t3-env are stubbed. `next/image` loads images unoptimized. An SVG imported as a component, like `logo.svg?react`, renders an `<svg>`. In a Next app, Node's modules like `path` resolve to the browser polyfills Next bundles for client code. A repo can add its own setup on top, such as its mock API and a logged-in user. Components are verified on several pages at once.
3. **Choose props** from each prop's type: every union case, `null`, empty and one-item arrays, an element for an element-typed prop, a resolved promise for a promise, and every literal the render compares a prop against. A function returns a sample of its return type, and an object with more fields than are sampled, like a TanStack table, answers the rest with a stand-in. Untyped props also take the literals their call sites pass, and a component that passes its props on whole, like `templateCtx(props)`, mounts with a sample of its whole props type, or of the props its type requires when it takes them as a rest spread, like a `FormField`'s `name` and `render`. A DOM node, like a portal's container, is left unset. Untyped props are shaped by what the component reads from them, like `booking.guests.fullName`. A `Date` is a date, and so is a string named like one, such as `createdAt`, and a string named `currencyCode` is a currency code, since the component parses them.
4. **Explore.** Click every enabled handler and type into every input, breadth-first, a few steps deep, waiting for requests to settle after each step. Read the fiber tree, hook values and probes after each one.
5. **Score** each screen against the predicted states. Every state region must match, and an action must move the regions it changes to predicted states and leave the rest alone. A child component's handler may change any hook or context value the component reads.

| Check       | Counterexample when                                                                                                                                        |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| State       | A screen, at the first commit or once settled, matches no predicted state.                                                                                 |
| Transition  | An action led somewhere unpredicted, or a handler the analyzer didn't model changed the screen. Unchanged counts only for prop calls or async transitions. |
| Effect      | The screen changed after the first commit without a predicted effect, unless it reads hook or context data.                                                |
| Value       | A `useState` or `useReducer` value fell outside the predicted set.                                                                                         |
| Unreachable | A branch side the analyzer called unreachable ran.                                                                                                         |
| Mutation    | A warned mutation never wrote to its state or prop, or a lost update re-rendered.                                                                          |

Each counterexample says what differed, like `expected <p> "Saved", found <p> "Error"`. A component whose states were truncated can't be refuted by a screen it doesn't predict. A component that **couldn't mount** isn't a counterexample; its failure is classified (`provider`, `env`, `module`, `missing-data`, `server-component`, `too-large`, `unresponsive` and so on) so the next harness fix is obvious.

Planting 14 realistic bugs in the analyzer, the verifier catches 13. The one it misses flips the async flag on an effect transition, which a page can't observe.
