# Viewer

Shows a component's source with the analyzer's findings drawn over it.

```sh
pnpm --filter bippy-analyzer viewer
```

Open http://localhost:3200/ and pick one of the five demos. Each is a fixture from the analyzer's tests, opened by path as `?file=<path>`; the viewer finds the nearest `tsconfig.json` above it. The legend on the right follows the component under the pointer: hover a line or a token and it switches, and it stays on the last one you touched. It starts on the component with the most states. The query string carries the view as `?view=diagram` or `?view=json`.

The Diagram tab collapses each component to its declaration line, one row per analyzed line in between with the variable's value set, the action's assignments and transitions, or the condition's arms and the states they appear in, and an MDP graph laid out by dagre: a node per state with its conditions and what it renders, and an edge per transition labeled with the action. The JSON tab shows the analyzer's own output for the file. The legend is a sidebar listing every component in the file as a collapsible panel; the component under the pointer opens, is marked with a bar and scrolls into view, and any panel can be opened or closed by hand; opening one scrolls the code or the diagram to that component. The sidebar collapses with its toolbar button or Cmd+B, opens as a sheet on phones, and stays collapsed in JSON mode.

Every state variable gets a color. In the source, its declaration, the calls that set it, the conditions that read it and the handlers that set it share that color. A dashed arrow curves from each setter call up to the declaration, and a solid arrow from the declaration down to each condition that reads it. Hovering anything lights its whole causal chain and dims the rest of the code; the diagram never dims. The right side uses MDP terms: the state variables, the states with their conditions and what they render, and the actions, each with the variables it sets and the transitions `S1 → S2` it causes, in the same colors. Hovering anything on either side isolates that variable.

The code is rendered by `@pierre/diffs`. The overlay measures each token inside its shadow root, by the `data-line` cell for the line and a text range for the columns, so it follows wrapping and resizing.

The viewer is its own workspace package, `bippy-analyzer-viewer`, a Next.js app under `viewer/`; `pnpm --filter bippy-analyzer viewer` starts it. The API is one Hono app in `src/app/api`, and it does not import the analyzer: it talks over stdio to a worker, `src/server/worker.ts`, that `src/instrumentation.ts` starts with tsx when the server boots. The worker analyzes the five demos right away, so the first click does not wait on TypeScript. The worker runs the analyzer and serializes its output the same way `analyze --json` does, and the page is built from that JSON alone. `src/server/analyzer-json.ts` reads and resolves the output, `src/server/view-model.ts` turns it into what the page needs, and `src/server/code-graph.ts` finds where each identifier sits in the text with Babel. The page is server rendered with the demo list in the HTML, and the client prefetches every demo's analysis and the highlighter while the list is on screen, so opening one is a cache hit. Next.js 16 type checks with the TypeScript 7 CLI, React Compiler is on, the dev indicators are off, and Inter is served through `next/font` from the `@fontsource-variable/inter` file. The client is a `Viewer` compound component, `Viewer.Toolbar`, `Viewer.Source`, `Viewer.Legend` and `Viewer.Status`, over a context that holds the file, the active component, the colors and the hovered token, with TanStack Query for the data.
