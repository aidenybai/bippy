The execution engine

How the React interpreter actually works

The central trick is to execute a program without always reducing an expression to one JavaScript value. A variable can hold “2 when this condition is true, 3 otherwise.” Objects, function calls, state updates, and returned elements carry that uncertainty forward.

This requires an interpreter, not a search for JSX. The engine reads syntax nodes, resolves names, calls functions, changes modeled objects, and schedules callbacks. For React, it gives real React a proxy component whose body calls the interpreter. React constructs fibers; the interpreter decides what elements the application body can return.

There are three things to keep separate throughout: the value an operation produces, the state it changes, and the condition under which it happened. Most of the complicated machinery exists because losing any one of those changes what the program means.

The examples below explain the implementation at the linked revision. Interactive traces are teaching models, not a browser-hosted copy of the analyzer. The main explanation is visible; expandable notes cover narrower implementation caveats.

Start with a component that changes over time

Suppose canEdit is an unknown Boolean. The component below uses it three times: to mutate a local object, to decide whether to register a timer, and to select an element. All three reads must refer to the same input. 

interface AccessPanelProps { canEdit: boolean }

const AccessPanel = ({ canEdit }: AccessPanelProps) => {
  const [isReady, setReady] = useState(false);
  const view = { mode: "read" };
  if (canEdit) view.mode = "edit";

  useEffect(() => {
    if (canEdit) setTimeout(() => setReady(true), 0);
  }, [canEdit]);

  return (
    <main>
      {canEdit ? <button>{view.mode}</button> : <p>{view.mode}</p>}
      {isReady ? <strong /> : <span />}
    </main>
  );
};

1. An element is a description

Creating an element records its type and props. The materializer gives React a proxy for AccessPanel. React invokes the proxy, which asks the interpreter to evaluate AccessPanel’s body.

Assume an ordinary mount without Strict Mode replay and a short timer inside the settling window. The tree view abbreviates host structure.

What exists after the first render?

A persistent hook cell contains false. A new local object contains a conditional field: view.mode is "edit" under canEdit and "read" otherwise. The effect callback has been recorded but has not yet registered a timer. The returned main element contains a conditional first child and a known span as its second child.

The application does not actually display a button and paragraph together. The analyzer can put both beneath internal branch markers in its intermediate React tree. Those markers preserve which child belongs to which condition. Later, the tree reader interprets them as alternatives rather than simultaneous UI.

What changes after the effect?

The proxy’s passive effect invokes the modeled callback. Its if is interpreted, so only the edit path registers a timer. The registration retains that guard. When the timer fires, setReady(true) is a conditional write to the persistent state cell, not an unconditional write to every possible execution.

The setter asks React to render the proxy again. The interpreter enters the component again with fresh local bindings but the same hook frame. It allocates a new view object; it does not reset the state cell to false. The later commit is caused by the edit-only update. 

Read-only execution:  p + span
Editable execution:   button + span → button + strong

Not an execution:     p + strong

Why is the last combination absent? Not because the engine recognizes a special “read-only page” pattern. It is because the same input condition survives the mutation, timer registration, setter call, and resulting commit. A plain set of possible values, without their conditions, would allow the engine to combine isReady = true with the wrong path.

The machine underneath the React layer

Think of the analyzer as an implementation of selected JavaScript semantics whose values are richer than the JavaScript engine’s own values. The real JavaScript engine executes the analyzer. The analyzer executes the application’s syntax tree.

Parsing gives it instructions to interpret

The source graph parses code into an abstract syntax tree. A node for count * 2 says “binary expression, multiplication, identifier on the left, literal on the right.” It does not contain the result of multiplication. The interpreter has to compute that result. 

const doubled = count * 2;

Variable declaration
├─ binding: doubled
└─ initializer: binary expression (*)
   ├─ identifier: count
   └─ literal: 2

read count → construct primitive 2 → apply * → bind doubled

evaluateExpressionValue dispatches on the node’s kind. A literal constructs a primitive. An identifier performs lookup. An object expression allocates an object. A function expression captures an environment without running its body. A call expression resolves and invokes a modeled callable. JSX constructs a modeled element.

The wrapper evaluateExpression then applies the active guard to the result where the representation supports it. Evaluation also consumes steps. If the engine cannot keep interpreting an operation, it can return an unknown value with a reason rather than fabricate a concrete answer.

This is not one immutable state object passed through every instruction. The interpreter also owns mutable module tables, journals, guards, and task queues. A returned value and changes to those stores are separate outputs of evaluation.

Scopes are linked maps, not copies of all visible variables

A scope has a map of bindings and a parent scope. Lookup walks outward until it finds the name. A function call creates a child of the function’s captured scope. A nested block can add another scope. Assigning an existing lexical binding needs its owning scope, not a new map entry that accidentally shadows it.

The scope map contains modeled values. A binding to an object contains a reference to that modeled object, not a recursive copy of it. This is why two bindings can alias one object and why snapshotting scopes alone cannot undo a property write.

Module resolution and module execution are different jobs

The reusable graph knows where an import points and what declarations a file contains. The interpreter’s execution state records evaluated bindings. Looking up an export can evaluate a declaration and cache its modeled value. Reusing that value matters: importing a shared object twice must not allocate two unrelated objects.

A module binding currently being evaluated is marked IN_PROGRESS, so recursive binding evaluation is distinguishable from an unevaluated binding or a concrete undefined value. Mutating a module binding updates the execution table. Conditional writes to that table participate in journaling just like writes to shared objects.

Parsed modules can survive across separate analysis runs. Evaluated module mutations cannot silently survive into a fresh run. Otherwise a module counter, cache, or previous timer would change the meaning of the new execution.

TypeScript annotations are not runtime inputs. The interpreter unwraps constructs such as satisfies and type assertions and evaluates their underlying expressions. Declaring role: string does not supply either a concrete role or an unknown role; the caller or environment supplies the modeled value.

What a value looks like inside the interpreter

The analyzer does not put a magical unknown Boolean into a normal JavaScript variable and let V8 handle it. It uses tagged records. The tag tells the evaluator what operations are meaningful and what information is available. 

interface StaticPrimitiveValue {
  kind: "primitive";
  value: StaticPrimitive;
}

interface StaticBranchValue {
  kind: "branch";
  alternatives: StaticValue[];
  preferredIndex: number;
  reason: string;
  location: SourceLocation | null;
  predicate: string | null;
}

These are source shapes, with referenced types left unexpanded. A primitive wraps a concrete value. A branch contains possible values and the identity of the choice between them. The branch is itself a value: it can be stored in an object, passed to a function, or returned from a hook.

Concrete, finite, and unknown are different amounts of information

Representation Information retained Consequence
Primitive 2 One numeric value. Multiplying by 2 produces 4.
A branch of 2 and 3 Two values and the choice relating them. Multiplication can produce a branch of 4 and 6.
Unknown number A primitive category, possibly with range or origin information. The engine can know it is numeric without knowing its magnitude.
Unknown value A reason and source location, but less information about the value itself. Operations may need to retain broader uncertainty.
Known object with unknown field Object identity and its known property structure. Other fields can still be read concretely.

Unknown is not undefined. Undefined is a particular primitive with well-defined nullish and truthiness behavior. Replacing uncertainty with undefined would choose outcomes the source did not choose.

A branch is normalized when it is constructed

branchValue does more than wrap an array. It first checks whether all alternatives are interchangeable. If they are, it returns one value. Otherwise it flattens nested branches, deduplicates interchangeable alternatives, adjusts the preferred index, and composes the predicate when flattening changes the alternative positions. 

flag ? 4 : 4                 → one primitive 4
flag ? 4 : 6                 → a two-alternative value
outer ? (inner ? A : B) : C   → flattened alternatives
                                with composed conditions

The composed conditions are essential. Flattening the last expression to [A, B, C] alone loses that A requires outer and inner, B requires outer and not inner, and C requires not outer. Changing the representation must not silently change which inputs select each result.

The preferred alternative is an evaluation preference, not a statement that the input is known. And equal-looking objects are not automatically interchangeable: two separately allocated objects can be distinguished by identity even when their properties are the same.

Unknown primitives can have useful shape

An unknown string may retain a prefix, a minimum length, or a fixed length. An unknown number may retain a range. A string with a known nonempty prefix is truthy even if its suffix is unknown; a range that excludes zero can also decide truthiness. Not knowing the complete value does not require forgetting every property of it.

String composition can preserve that two strings were constructed from the same uncertain source with the same prefix and suffix. That matters for using generated strings as property keys: a later read must be able to refer to the same unknown key that an earlier write used.

Other tags cover lists, functions, elements, React APIs, native functions, external bindings, contexts, and repeats. The purpose is not merely classification. Each tag selects a different operational path when code tries to call, read, mutate, iterate, or render the value.

How an operation carries uncertainty forward

For a concrete operand, a modeled operation can compute a concrete answer. For a finite branch, it can apply the operation to the alternatives and rebuild the result around the original decision. 

const count = flag ? 2 : 3;
const doubled = count * 2;

Mapping a value is not forking an execution

mapValue calls a transform once for a non-branch value or once per alternative for a branch. joinMappedAlternatives reconstructs the result using the source branch’s reason, predicate, and preference, retaining branch origin where needed.

That is enough for a value transformation without relevant shared writes. It is not enough for a callback that mutates an object. Mapping evaluates alternatives in sequence; by itself it does not restore a heap between them. The interpreter needs a journaled fork when alternative evaluation changes shared state. 

Value mapping:
  alternative → transformed alternative
  preserve the selecting decision

Execution forking:
  save entry state
  execute a path → value + mutations + completion
  restore entry state before its sibling
  join the resulting values and stores

Two branched operands need correlated pairing

If left and right are both conditional, evaluating an operator over every possible pair can introduce impossible combinations. Consider two values derived from one flag: 

const left = flag ? 1 : 2;
const right = flag ? 10 : 20;
const sum = left + right;

Native JavaScript permits the pairs 1 with 10 and 2 with 20, giving 11 or 22. The binary-distribution helper has a paired path when both branch records share a non-null predicate and aligned alternative counts. In that case it applies the operator to corresponding slots instead of building a cross-product. Otherwise it distributes a small product through nested branch values.

That mechanism is not a guarantee that every source-level relationship reaches the operator intact. With the flag supplied as an unknown declared Boolean in this example, the pinned engine’s resulting model includes 11, 12, 21, and 22. The two extra sums expose a lost pairing. The important implementation dependency is that the input’s relationship must survive into the branch metadata the operator actually reads; having a paired-operation helper alone does not establish that.

Short-circuiting is about whether the right side executes

&&, ||, and ?? do not simply compute both operands and select an answer. Evaluating the right operand can throw, mutate, or register work. The right operand must not run on a path that skips it. 

let calls = 0;
const getFallback = () => {
  calls += 1;
  return "fallback";
};
const value = input ?? getFallback();

For input 0, the result is 0 and calls stays 0. For null or undefined, the result is the fallback and calls becomes 1. For an uncertain input, both the returned value and the mutation need the appropriate condition. Nullishness is not truthiness: false, 0, and an empty string all skip this fallback.

The distinction between mapping and forking is concrete here. In the pinned implementation, && and || use tested, journaled paths. ?? maps alternatives and caches a right-side evaluation. With input = flag ? null : 0, that can produce 0:1 for the result and call count instead of 0:0. The value selection survives while the conditionality of the write is lost.

A property read can itself execute code

Reading a plain known field returns its modeled value. Reading a getter invokes a modeled callable with the receiver. A computed property first needs a modeled key. Reading through an uncertain receiver may require evaluating alternatives. Thus object.value is not always an inert lookup.

Optional chaining needs another distinction: “the receiver was nullish, so skip the remaining chain” is different from “a property read produced undefined.” The engine uses a short-circuit marker through the chain and converts it to undefined at the enclosing chain boundary. That keeps the decision to skip separate from the ordinary value undefined.

A function is source code plus an environment

Evaluating a function expression does not run its body. It creates a modeled function value containing its syntax node, module, captured scope, receiver-related information, and properties. The captured scope is what makes it a closure.

A call creates a new activation, not a new universe

evaluateFunctionBody creates a scope whose parent is functionValue.scope. It binds parameters to the argument values and sets up the call context. For a non-arrow function it also supplies an arguments list. The call shares the relevant interpreter state, hook frame, and evaluation budget rather than starting the whole analysis again. 

const getAccess = (role: string) => ({
  canEdit: role === "admin",
});

const access = getAccess(role);
const showButton = access.canEdit;

The argument is the original modeled role value. Parameter binding does not invent an unrelated unknown called role. The helper evaluates its equality test, allocates an object, and returns it. Reading access.canEdit retrieves the derived result. Its relation to the original input can survive the call and the returned container.

Capturing a binding is not freezing its answer

const state = { label: "before" };
const readLabel = () => state.label;
state.label = "after";

The function reads object A when called. Its captured reference still reaches A after A’s contents change.

If the closure captures a primitive binding that is later reassigned, it needs the binding’s later value. If a later React render creates an entirely new scope with a new count binding, an older callback still refers to its original scope. These are different situations. “Closures have stale values” is not a general rule; environment identity is the rule.

The same function body can produce different function identities

const makeReader = (label: string) => () => label;
const readFirst = makeReader("first");
const readSecond = makeReader("second");

The inner arrow has one syntax node, but the two evaluations capture different call scopes. Treating a function as only its AST node would make both readers share the wrong label. This also matters for React: component functions returned by separate factory calls must not automatically become one component type just because they share source text.

Calling is a dispatch, too

The callee may be an interpreted function, a native-function model, a built-in method, a React API, or an uncertain choice of callables. The engine dispatches accordingly. An interpreted function enters its body; a modeled setter updates hook storage; an array method evaluates callbacks according to its model.

An uncertain callable can require callAlternatives. Each alternative call gets its own journaled path and guard because different callees can produce different mutations. An ordinary property method call also carries the receiver, while a detached call has different receiver semantics. Bound arguments and a bound receiver are applied before entering the body.

Recursion is handled operationally. The interpreter tracks calls, arguments, receivers, mutations, and fork depth to detect non-progressing recursion, and it has a call-depth limit. It can produce unknown rather than recurse forever. It is not solving an arbitrary recursive equation to completion.

Conditions have identity and structure

An unknown input is useful only if repeated uses can refer to the same uncertainty. Otherwise every read becomes a fresh choice and the engine manufactures combinations that the program cannot produce. 

<nav>
  {role === "admin" && <button />}
  {role === "admin" && <a />}

The two tests derive from the same role input. Selecting only one child would require a condition and its negation to hold together.

Derivation tracking connects values back to inputs

The predicate machinery records relationships such as property access, aliases, equality, comparisons, negation, and refinements. A test can then become a structured condition like eq(input1, "admin") rather than a free-floating Boolean with no origin.

The name “role” alone is not the identity. Two separate function calls can both have a parameter named role while receiving different inputs. Conversely, role can be renamed to permission, passed through a helper, and read from an object while still deriving from the same input.

Narrowing is a temporary assumption while evaluating a path

When a supported test restricts an identifier or property, evaluateTestedPaths can evaluate each side with an appropriately narrowed value. The true side of a null check should not continue treating the checked binding as definitely null. The sibling path gets its own restriction, and the outer state is restored and joined afterward.

Narrowing does not globally assert that the input has the selected value. It says “inside this path, interpret operations under this assumption.” A branch that the narrowing makes impossible can be skipped entirely.

Nested conditions combine; alternatives do not become independent

if (isSignedIn) {
  if (canEdit) showEditor();
}

The inner call requires both conditions. Its guard is the parent guard AND the inner guard. If either input rules it out, the call does not belong to that execution. Several independently sufficient reasons for an update can instead be combined with OR.

The solver checks the constraints that the representation supplies: truthiness, supported equality, membership, numeric comparisons, and type constraints. It is not an oracle for arbitrary JavaScript. If an earlier operation lost the derivation, the solver cannot reconstruct that missing relation just because two expressions look similar in the source.

Keep three identities distinct: an input identifies uncertainty in a value; a predicate describes a relationship over inputs; a branch occurrence identifies a particular choice in a tree or computation. Different occurrences can depend on the same predicate.

A branch with side effects cannot be modeled by simply running the true side and then the false side. The false side would observe a history that belongs to the true side. It has to start from the same entry state.

The journal is keyed by the mutated thing

HeapJournal keeps maps for object contents, list state, custom journaled state, module bindings, and pending hook updates. An object map is keyed by the modeled object itself. That matters because a write through alias must be recognized as a write to the same object reached through state.

Before a preexisting object is first changed, the journal saves its original entries. At endPath, it records the contents that path left and puts the original entries back. The same pattern applies to arrays and their named properties, mutable API models with capture/restore operations, and the other tracked stores.

The joined object is still the same object

The engine cannot replace just one alias with a fresh merged object. A closure, collection, or another binding may still reach the original. The join changes the contents of the modeled object while preserving its identity relationships. Afterward state === alias can remain true while state.count is conditional.

Lexical bindings are snapshotted and joined separately. A reassignment such as state = anotherObject changes which value the name points to; a property assignment such as state.count = 1 changes the object reached through the name. Both are mutations, but restoring one does not restore the other.

The path that did nothing still contributes a state

For if (flag) state.count = 1, the false path contributes the original count. It does not contribute “no value.” For a conditional reducer dispatch, the untouched path contributes an empty action sequence. For a timer cancelled on one path, the other path contributes a still-live registration.

Pending hook updates are especially revealing. The journal captures pending next state, reducer actions, deferred updates, and whether the setter escaped. A conditional setter cannot leave an unconditional pending value behind merely because the setter itself returned undefined on both paths.

Objects allocated inside a path have a different lifetime

The journal remembers the allocation ordinal at fork entry. An object allocated afterward did not exist in the sibling’s starting state. It generally does not need the same restoration as a preexisting shared object. A new object can remain a path-specific returned alternative; its identity must not be confused with a preexisting object whose fields were changed.

Joining values and joining effects are separate operations

Two paths can both return 0 and leave different counts. Their return value collapses to one primitive; their heap cannot. Conversely, two different returned numbers can leave the same heap. The engine must join each kind of state according to what actually differed, not infer the store from the shape of the return value.

The entire design depends on writes going through the appropriate mutation hook. An internal iterator cursor stored outside the journal can still leak from one explored path into the next. Restoring ordinary objects is not automatically enough to restore every mutable API model.

A value is not enough to describe control flow

An expression produces a value. A statement list also needs to say whether execution can continue. Returning 7 and producing 7 while falling through are not the same result: only the second permits the next statement to run. 

const box = { value: 0 };
const choose = () => {
  if (flag) {
    box.value = 1;
    return "early";
  }
  box.value = 2;
  return "late";
};
const label = choose();

The outcomes are early:1 and late:2. If the engine first joined box.value and then ran the rest of the function unconditionally, the later write would overwrite the early-return path too. Keeping a branch in the returned label would not repair the heap.

StatementOutcome carries completion information

interface StatementOutcome {
  returned: StaticValue | null;
  mayComplete: boolean;
  completion?: StaticValue;
  jump: LoopJump | "uncertain" | null;
  isSuspended: boolean;
}

returned gathers modeled return outcomes. mayComplete says whether any path falls through. The optional completion value can describe that condition more precisely. A jump represents loop control. Suspension says that the remainder awaits another event rather than having completed normally.

The final function result is derived from this outcome. If the body can fall through without returning, undefined is an alternative under the fall-through condition. The engine cannot silently drop that path just because another path returned a useful value.

forkPaths passes the rest of the computation as a continuation

A continuation here is the code that should run next, packaged as an interpreter callback. It is not necessarily an application promise callback. The statement evaluator passes a proceed continuation so a branch can decide which states are allowed to reach the rest of the statement list. 

if (flag) return "early";
box.value = 2;
return "late";

true path:   preserve its return and heap; do not call the rest
false path:  continue with box.value = 2, then return
join:        combine the finished executions, not their prefixes

forkPaths separates completing paths from jumping or returning paths. When only some paths continue, journal.continueFrom joins the stores of those completing paths into the live store for the continuation. The exited paths remain separate. After the rest runs, its end state is joined with the exited end states.

The continuation runs under the OR of the conditions of paths that can reach it, combined with the parent guard. Returning closures require additional scope handling because they may retain bindings from a path that already exited. A function return ends execution of that path, not the lifetime of every object or environment it created.

Throws carry a payload and an abrupt outcome

A modeled throw must retain what was thrown, including undefined, null, or an object reference. It must not be confused with an ordinary unknown result. The interpreter’s throw representation carries the payload so catch binding can recover it and preserve its identity.

A try statement separates paths that pass through from paths that throw into the handler. The catch block gets a child scope with the caught value bound to its parameter. Mutations made before the throw are not automatically rolled back: a catch can observe them. Journaling separates alternative executions; it is not a transaction that reverses JavaScript exceptions.

Finally runs on exits, and can replace the exit

const choose = () => {
  try {
    return "from try";
  } finally {
    return "from finally";
  }
};

A normal finalizer preserves the pending return or throw while adding its effects. An abruptly completing finalizer supplies the new exit instead. evaluateTry therefore has separate handling for continuing execution and already-exiting outcomes; merely appending the finalizer after the try block would miss returns and throws.

Break and continue are different exits again: they leave a loop body in different ways, not necessarily the enclosing function. Await suspension needs to retain the relevant completion handlers so eventual fulfillment or rejection can continue through the right catch and finally behavior. These mechanisms are implemented for supported forms; they are not a claim of complete support for every JavaScript control-flow form.

How JSX becomes something React can render

An interpreted element is not a fiber. It is a description of a type, key, modeled props, source location, environment, and owner. React produces fibers later, when the materialized description is reconciled.

Evaluating JSX does not call the component body

const child = <Toolbar role={role} />;

The interpreter evaluates the attributes, resolves the element type, and evaluates child expressions. It then constructs a modeled element, or calls a configured JSX factory when appropriate. For a component element, this records the component and props. It does not eagerly substitute the Toolbar function’s returned JSX.

JSX text is normalized and entities are decoded. Expression children are interpreted. A spread child can expand a known modeled list; an unsupported spread retains uncertainty. Lowercase host tags and component references lead to different materialization paths.

The proxy is the bridge between two execution systems

React cannot interpret a StaticBranchValue as an ordinary React child. The materializer translates modeled values into real React nodes. For an application function, it creates or reuses a real function component that calls the interpreter when React renders it.

That proxy has a persistent instance and hook frame. Its returned React nodes come from materializing the modeled result. React then handles reconciliation, fiber ancestry, mounting, and the proxy’s real effect phases. The original application body still runs through the interpreter, so it can carry uncertain values.

This is why the engine is neither “just execute the app” nor “implement another reconciler.” It substitutes interpreted component bodies into a real reconciliation process.

An unknown child and an absent child mean different things

Known false, null, and undefined children contribute no visible child. A concrete element is materialized. A finite branch becomes a choice with alternatives. A repeated value can become repeat markers. An unresolved child needs a marker for unresolved structure; it cannot simply disappear because the interpreter does not know it.

A branch marker holds multiple alternatives in one intermediate tree

branchNode creates internal branch and alternative components. Real React can mount these markers and the proxies beneath them. The analyzer’s tree reader later recognizes the marker shapes and reconstructs a conditional pattern. 

Intermediate carrier                  Meaning

$Branch(flag)                         choose under flag:
├─ $Alternative(true)                   button
│  └─ button                          choose under !flag:
└─ $Alternative(false)                  p
   └─ p

Mounting alternatives in one carrier makes shared effects delicate. If a component increments a module variable during render, rendering one alternative can change the value seen by another unless that state is isolated. “React constructed the tree” does not itself isolate hypothetical worlds.

Identity controls which instance persists

The materializer caches proxy types by modeled component identity. A proxy created anew for every encounter would appear to React as a different component type and reset its instance. Collapsing distinct captured component closures to one proxy would make the opposite mistake.

Keys and tree position still matter because real React uses them during reconciliation. Internal marker ancestry matters too: removing or moving a marker can change the position under which a proxy mounts. A representation change can therefore change hook lifetime even when the visible host elements look the same.

The element owner is also distinct from its eventual parent. An element can be created in one component and passed as children through another. The recorded owner helps retain where creation happened rather than inferring it only from eventual fiber ancestry.

Inside a hook frame

Application hooks do not store uncertain values in React’s ordinary state hooks. They use analyzer-owned storage associated with one mounted proxy instance. The proxy uses real React hooks to retain that storage and request another render.

Call order finds the cell

beginHookPass resets the frame’s cursors and current-pass effect list, not the persistent cells. A state hook advances the state cursor. If that index already has a cell, the cell is reused; otherwise the initializer creates it. Memo-like hooks use a separate array and cursor in this implementation. 

Mounted proxy instance
└─ HookFrame
   ├─ cells[0]       current, next, setter, reducer actions, deferred values

   ├─ memoCells      memo values, callbacks, refs and dependencies
   ├─ effects       records from this evaluated pass
   └─ previousEffects  records from the committed pass

A component’s render-local variables are different storage. They are bindings in a function activation. A subsequent evaluation creates new bindings that read the persistent cells. An old effect callback can keep its old activation alive.

A StateCell separates current, pending, and deferred values

interface StateCell {
  name: string;
  initial: StaticValue;
  current: StaticValue;
  next: StaticValue | null;
  pendingReducerActions: StaticValue | null;
  setter: StaticNativeFunctionValue | null;

current is what the hook reads. next is a pending computed state; null here means no pending update, not the application state null. Deferred values represent updates whose timing is not pinned to the current synchronous execution. An escaped setter means code outside the followed execution may update the cell.

The setter is created once for the cell. It captures the frame and cell it updates, not merely the latest local variable name. This permits an older callback to use the same setter after later renders.

The modeled state setter computes pending state eagerly

For useState, a functional updater is interpreted against cell.next ?? cell.current. Its result becomes the pending value. This is the implementation’s simplified update mechanism, not React’s full lane-based update queue.

Two replacement calls from a callback whose count is 0 both supply 1. Two updater functions can compute 1 and then 2 because the second receives the first pending result. The callback’s captured count remains 0 in either case. Unchanged updates can be dropped using decided identity or modeled value equivalence.

A normal update outside render requests another proxy render. commitHookPass applies pending state before the next evaluation, then beginHookPass resets cursors. Render-phase updates can trigger additional interpreted passes within the proxy’s render handling. Repeatedly changing state eventually causes the affected cells to become unknown rather than permitting infinite settling.

A reducer stores actions rather than only a computed next state

Modeled useReducer appends actions to an ordered modeled list. The hook pass calls the reducer with accumulated state and each action. Conditional dispatch produces conditional action sequences. No dispatch is an empty sequence; it must not be replaced by a mystery action.

This differs from useState’s eager updater calculation. Both may eventually yield a next state, but the time at which application code is called and the intermediate storage differ.

Refs and memoized values preserve different things

useRef retains a modeled object in memo storage. A write to current changes that object but does not request a render on its own. Closures that share the ref can see the changed field because the object identity survives, even when their primitive state bindings are older.

useMemo reuses the stored modeled result when dependencies compare equal, otherwise it invokes the factory. useCallback retains the callback value rather than invoking it. A callback can therefore remain the same function value, with the same captured scope, even though the component body has been evaluated again.

If a setter escapes to unknown code, the engine cannot assume the initial state is permanent. It can retain initial state or an unknown updated state. Known deferred updates may contribute more specific alternatives. These possibilities describe uncertainty in the state cell; they are not an automatically generated sequence of clicks.

Where this intentionally differs from the full React scheduler

The real reconciler schedules the proxy, but the analyzer’s application state model does not reproduce every concurrent lane or transition state. At this revision, modeled useTransition returns false for pending and invokes its callback immediately; useDeferredValue returns the input. Strict Mode-related duplicate factory invocation is modeled in selected hook paths. None of that turns the hook frame into a copy of all React internals.

An effect has a callback, a lifetime, and a cause

Rendering an application effect records work. It does not execute that effect inline. The record contains whether it is a layout effect, the modeled callback, its dependencies, and a cleanup slot.

Rendering, committing, and running an effect are separate events

Evaluate component body
  → record effect callback + dependencies
  → return modeled elements

React commits the proxy tree
  → proxy layout effect runs modeled layout effects
  → proxy passive effect runs modeled passive effects
  → those callbacks may queue state updates or tasks

A new render can create a new callback function without that callback necessarily executing. The engine compares the current effect record with the previous committed record. For known dependency lists, it checks length and uses its hook-value identity/equivalence comparison for corresponding members.

If dependencies are unchanged, the effect keeps its previous cleanup. If they changed, old cleanups in that phase run before new callbacks in that phase. The value returned by a callback becomes the stored cleanup when it is callable. On unmount, the cleanup is associated with the effect that ran, not an arbitrary newer closure.

Registration must preserve the condition that created a callback

useEffect(() => {
  if (enabled) {
    const handle = setTimeout(() => setReady(true), 0);
    return () => clearTimeout(handle);
  }
}, [enabled]);

The timer exists only under enabled. The cleanup for that path refers to that timer’s handle. If an unrelated state update commits before the timer runs, the timer must not inherit the unrelated commit’s cause. Its registration has already established why the callback exists.

CommitCauses maintains an active cause while work runs, collects pending causes when updates are scheduled, and associates the resulting commit with those causes. Binding a task captures the current cause. Running a continuation combines its captured condition with the applicable execution condition instead of consulting only whichever commit happened most recently.

A cause must constrain writes, not only callback eligibility

Suppose a callback is possible under enabled but enabled is still unknown. “This callback might run” is not permission to apply its setter unconditionally. The disabled path must keep its old state.

The materializer’s runGuardedMutation routes such work through the interpreter’s conditional mutation machinery. Conceptually it joins a path that runs the callback with the path that does not, while retaining the guard. Shared-store writes, reducer actions, and pending state all need this treatment. 

Callback registration condition: enabled
Callback body:                   setReady(true)

Correct joined state:
  enabled  → ready may become true
  !enabled → ready stays false

Insufficient:
  ready is false or true, unrelated to enabled

Nested requirements combine with AND. Several sufficient update causes can combine with OR. The initial mount does not need a preceding setter, so its cause is unconditional. Later commits can be conditional even when the intermediate reconciler has constructed one physical tree for multiple possibilities.

Why cleanup ordering matters to state, not just resource hygiene

A cleanup can cancel a task, unsubscribe a listener, or mutate shared state before a new effect registers its replacement. Reversing that order can cancel the wrong registration or let an obsolete callback update a cell. An analyzer concerned only with the final JSX would miss these causal changes entirely.

The proxy also coordinates modeled microtask draining with layout and passive phases. Passive effects can occur after queued microtasks in a later task, while synchronous commit paths require different handling. The implementation distinguishes those cases rather than treating every effect as “run immediately after the function returns.”

Promises are state machines; awaits suspend computations

A modeled promise is not just an unknown eventual value. It has identity, mutable settlement state, and registered reactions. A promise can already be fulfilled while its then callback is still waiting in the microtask queue.

Settlement and reaction execution happen separately

ModeledPromise associates a modeled object value with internal promise state and a reaction list. The implementation represents pending, settled, following, and escaped states. A settled outcome can be a fulfillment value or a thrown outcome representing rejection.

Resolving a promise establishes its outcome; reactions are scheduled work that receives that outcome. Following another modeled promise retains the dependency on its settlement. An additional resolve must not overwrite an already determined result. Conditional settlement has to remain conditional after branch joins, so promise state implements capture, restore, and join.

Known pending and externally settled are different

A promise can be pending while the interpreter knows the queued code that will settle it. The engine can advance that work and resume the body. A promise that depends on code outside the analyzed execution has uncertain timing and possibly an uncertain value.

When settlement escapes, the model can resume under uncertain fulfillment or rejection outcomes and mark the result as escaped. State updates after that point may be recorded as deferred possibilities rather than assumed to have happened before the current commit. This avoids turning “could finish later” into “already finished now.”

A framework-awaited component call also differs from an ordinary application callback. The framework path can ask the interpreter to obtain the awaited result as part of producing the tree. That is a policy of that call boundary, not a universal rule that every async application operation settles before rendering.

A timer handle identifies one piece of work

Registering a timer creates a task record with its callback, delay information, identity, and condition. Clearing a handle affects that registration, not every timer with a similar body. Conditional cancellation must not cancel the timer on paths where cancellation never happened.

The renderer settles work by alternating eligible modeled tasks with React flushes. It does not wait through arbitrary wall-clock time or enumerate every browser scheduling interleaving. Long or dynamic delays can stay deferred. Timing uncertainty can therefore change how a state update is represented even when its new value is known.

Async and generator forms are not uniformly implemented

Continuation handling is stronger for some statement forms than for arbitrary nested await expressions. Concise async-arrow bodies and non-leading awaits have semantic gaps at this revision. Generators use a different model: the body is evaluated eagerly to collect yields, then an iterator replays them. That differs from native JavaScript’s suspension between generator next calls. Do not infer one construct’s execution rules from the fact that another construct also uses the word “suspend.”

Arrays are values; iteration is execution

A modeled list has item values, identity, and possibly named properties. A list can be known even if some of its items are uncertain. Calling map on it is not the same as scanning the callback for an element name. 

const rows = items.map((item) => (
  <Row key={item.id} label={item.label} />
));

For a known finite list, the model supplies callback arguments for its items and interprets the callback. Property reads, helper calls, returned elements, throws, and shared mutations inside that callback all matter. Three known records can therefore produce three specific modeled elements, not just a generic “Row exists” fact.

Filtering changes presence, not only item content

If an item’s inclusion condition is uncertain, the collection result needs to represent that the item may be absent. Replacing the item with an unknown value is not equivalent: an absent item changes length and child positions, while an unknown present item still occupies an occurrence.

A callback that might not run also has conditional effects. If a filter or uncertain iteration causes only some paths to call a callback, writes made by that callback have to join with the untouched state. The interpreter’s runMaybe mechanism explicitly models code that may execute or may not execute from the same entry state.

Known loops can unroll; an unknown tail cannot be guessed away

A loop over a known iterable can execute its modeled items, subject to the overall step budget. A conditional loop can unroll while its test remains decidable. The implementation bounds concrete unrolling of conditional loops, then summarizes uncertain remaining work rather than pretending it has established termination.

Loop-carried bindings are values changed by one iteration and read by another. If their later values cannot be retained finitely, widening gives up some precision. The code after the loop must then receive that uncertainty. Running a few iterations and keeping their last concrete value would misdescribe a tail that can still change it.

Break and continue feed into completion handling. A return inside a callback or loop has to be associated with the appropriate function or loop continuation. A mutation made before the jump still belongs to that execution.

Repeat is a structural summary, not a concrete array

Known list:          row(A), row(B), row(C)
Conditional member: row(A), enabled ? row(B) : nothing
Repeated pattern:   row(item) × some permitted number of occurrences

A repeat retains an item pattern and cardinality information. It lets the tree represent repeated structure without choosing a final concrete length. A bounded list of expanded trees is only one possible view of that representation; the repeat is not secretly a fixed-size array.

Inputs inside the repeated pattern need the right scope. An unknown status belonging to each row should not force all rows to have the same status. An outer permission flag read by every row should remain shared. The pattern representation distinguishes iteration-local inputs from shared inputs.

Mutation inside an iterator is still mutation

A Set or Map iterator has a cursor. Advancing it changes what the next call returns even if the underlying collection does not change. A combined analysis must restore that cursor when exploring siblings just as it restores an object field.

At this revision, collection iterators reuse a generator representation with mutable cursor state outside the ordinary heap journal. That is a concrete example of why modeling the collection’s entries is not enough: the execution protocol around those entries has state too.

Values also arrive from outside the function

Props are not the only source of input. Components read providers, external stores, browser APIs, package exports, caches, and module state. The engine needs an operational meaning for those reads or an explicit uncertainty where that meaning is unavailable.

Context uses real ancestry with modeled contents

The materializer associates a modeled context definition with a real React context. A provider carries a modeled value through that real context. When the application’s modeled useContext runs, it reads the provider value at the proxy’s position rather than using one global value for every occurrence of the component. 

<ThemeContext.Provider value={firstTheme}>
  <Toolbar />
</ThemeContext.Provider>
<ThemeContext.Provider value={secondTheme}>
  <Toolbar />
</ThemeContext.Provider>

The Toolbar source is identical in both places. Its surrounding provider input is not. The proxy records context reads, and retaining a previous rendered result depends in part on those reads still resolving to the same modeled values.

An external store is read and subscribed, not just initialized once

The useSyncExternalStore model calls getSnapshot during render. A modeled passive effect subscribes to changes and rechecks the snapshot. A store change between rendering and subscription must not leave the component permanently stuck on the earlier snapshot.

The listener reads again and queues a state update when followed execution changes the store. If the listener is held by code outside the analyzed execution, the store may change without an observed call; escape handling broadens what the snapshot can be. That distinction separates known store transitions from “the outside world may update this.”

The result is a conditional tree, not a bag of screenshots

After React constructs the intermediate fibers, the tree reader translates them into patterns. Ordinary fibers become structural nodes. Internal branch markers become choices. Repeat markers become repeated patterns. Unresolved regions remain explicitly unresolved.

A concrete fiber pattern has a deliberately small shape

interface PatternFiber {
  kind: "fiber";
  tag: SnapshotWorkTag;
  name: string | null;
  key: string | null;
  children: PatternNode[];
}

The work tag identifies a category such as a function component or host component. Name and key retain structural identity information. Children recursively hold more patterns. This representation does not carry every original prop, event handler, computed style, or DOM property.

A branch has alternatives and guards; a commit has a guard too

A branch pattern retains its decision identity, reason, source location, inputs, and a guard for each alternative. A repeat retains its cardinality, count bounds, item pattern, and iteration-local inputs. A symbolic commit pairs a whole tree with the condition under which that commit applies. 

Initial commit, allowed unconditionally
  main
    branch on canEdit
      true  → button
      false → p

The commit guard is not interchangeable with the first child’s branch guard. The first says when this entire later state belongs to the execution. The second chooses a subtree within a state. Losing the commit guard would admit the later ready tree under a path that never scheduled its update.

Related decisions share input constraints. Independent decisions can be represented separately rather than immediately expanding every combination. The useful object is that constrained structure, not merely a long list of concrete trees.

Evaluation can know something that the tree does not retain

<output>{result}</output>
<output>result: {result}</output>

These child forms can take different React paths. For a scalar host string or number, React can set text content directly without a separate HostText fiber. In the first form, a concrete host pattern may therefore have no text child at all. Mixed text children can instead produce text fibers retained by the pattern.

Likewise, two different className values can result in the same structural fiber pattern. Computing a value during interpretation and preserving it in the final projection are separate decisions. The tree tells you component and element structure with conditions; it is not a complete state dump of the browser page.

An unresolved region is a kind of node, not an empty subtree

An opaque component records that its body was not available to the analysis. Passed children may still be represented as content that belongs somewhere inside it. A wildcard represents unresolved structure more broadly. Neither means that the real component renders nothing.

The same distinction holds throughout the interpreter: absence, a known empty value, a finite choice, and missing information are different meanings. The tree is useful only if the earlier stages keep those meanings separate all the way from expressions and mutations to the final patterns.
